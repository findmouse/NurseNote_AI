# NurseNote AI — アーキテクチャ設計書

> 生成 AI を活用した **看護記録（SOAP）・退院サマリー作成支援システム**
>
> 本システムは記録作成の **支援ツール** であり、記録内容の最終責任は看護師にあります。

| 項目 | 内容 |
|---|---|

| 想定利用者 | 病棟看護師 |
| 技術スタック | Vue 3 / FastAPI / PostgreSQL + pgvector / LangChain / Docker |

## 1. 背景と目的

### 1.1 課題

病棟看護師は、患者一人ひとりについて毎日の看護記録を作成する必要がある。
現場では **1 日あたり約 1 時間** が記録業務に費やされており、患者ケアの時間を圧迫している。
さらに退院時には退院サマリー、入院時には問診票・アナムネ聴取の文書化が必要となり、
文書作成の負担は看護師の離職要因のひとつにもなっている。

### 1.2 本システムの狙い

- 看護師は **バイタル値・チェック項目・短い自由記述** だけを入力する
- システムが **過去の看護記録と入院時情報を参照** し、規定の様式（SOAP など）で記録案を生成する
- 看護師が内容を確認・修正して **確定** することで、正式な記録となる

**目標：記録作成時間を 1 日 60 分から 15 分程度に短縮する。**

### 1.3 設計上の最重要原則

医療文書は法的証拠となる文書であり、AI が事実を創作することは絶対に許されない。
一方で、**看護記録から解釈をすべて取り除くこともできない。**
SOAP の A（アセスメント）は定義上、事実そのものではなく事実に基づく臨床的解釈だからである。

したがって「AI は推測してはならない」という単純な禁止では設計として成立しない。
必要なのは禁止ではなく **区別** である。

> ### 生成文のすべての記述に「それが何に由来するか」を持たせ、事実と解釈を混ぜない。

具体的には、生成文の各記述を次の 4 種類に分類する。

| # | 分類 | `source_type` | 例 | 由来 |
|---|---|---|---|---|
| ① | **直接事実** | `today_input` | 「体温 37.2℃」「食事 8 割摂取」 | 本日の入力 |
| ② | **歴史事実** | `historical_note` | 「前日も歩行時に疼痛あり」 | 過去の看護記録（`note:123`） |
| ②' | **患者背景** | `patient_profile` | 「ペニシリンにアレルギーあり」 | 入院時基礎情報 |
| ③ | **臨床的解釈** | `clinical_inference` | 「疼痛は前日と比較して軽減していると考えられる」 | ①②から導いた推論 |

③ は「原文に存在する事実」ではなく「事実からの推論」である。
これを ①② と同じ `supported = true` として扱うと、
**捏造（あってはならない）と推論（記録に必要）が同じ扱いになってしまう。**
両者は性質がまったく違うため、最初から別の型として設計する。

この原則を担保する仕組み：

| 仕組み | 内容 | 実装フェーズ |
|---|---|---|
| **根拠の型付け** | 構造化出力で、各記述に `source_type` と根拠 ID を必ず付けさせる | M2 |
| **フィールド単位の制約** | S / O には解釈を書かせない（§5.2）。Pydantic の validator で機械的に拒否する | M2 |
| **数値の非生成** | バイタル値は LLM を通さずテンプレートで直接埋め込む | M2 |
| **決定的検証（Layer 1）** | 数値・日付・患者の一致を **LLM を介さず Python / SQL で** 検証する（§5.3.2） | M3 |
| **意味的検証（Layer 2）** | 出典が本当にその記述を支持しているか、推論に飛躍がないかを LLM で検証する（§5.3） | M3 |
| **看護師による確定** | 生成物は `draft`。看護師が確認・修正して `confirmed` にするまで正式記録として扱わない。すべての操作を監査ログに残す | M2 |

**数値を LLM に生成させない**のは、数値の改変が最も危険な幻覚だからである。
バイタル値は入力値をそのままテンプレートに埋め込み、LLM は文章部分だけを担当する。

同じ理由から、**検証においても数値・日付・患者の一致は LLM に判定させない。**
「出典を正しく申告している」ことと「内容が正しい」ことは別問題であり、
後者のうち機械的に判定できるものは、モデルを介さない経路で確実に潰す（§5.3.2）。

## 3. 画面設計

### 3.0 前提：看護記録の対象は「入院中の患者」だけ

看護記録は入院中の患者に対して作成するものである。
したがって主画面の患者一覧に出てよいのは **担当病棟に現在入院中の患者だけ** であり、
退院済み・入院歴のない患者が混ざってはならない。

一方で、**新規入院を登録するときには「まだ入院していない患者」を探せなければならない**。
この 2 つは要件が正反対なので、検索を用途で分ける。

| 用途 | 対象範囲 | 病棟スコープ |
|---|---|---|
| 主画面の担当患者一覧 | `admissions.status = 'active'` の患者のみ | あり（自病棟のみ） |
| 新規入院登録時の患者検索 | 患者マスタ全体（未入院・退院済を含む） | なし（未入院の患者は病棟に属さないため） |

入院と退院は対の操作である。退院処理を用意しないと患者が担当一覧に残り続けるため、
**新規入院登録と退院処理はセットで実装する。**

### 3.1 基本方針：患者中心のナビゲーション

「入院時情報 / 看護記録 / 退院サマリー」を独立した 3 つの入口にすると、
機能ごとに患者を検索し直すことになり臨床の動線に合わない。

そこで **左側に患者一覧を常駐させ、患者を 1 回選択したら 3 つのタブが同じ患者に追従する** 構成とする。

```
┌────────────────────────────────────────────────────────┐
│ NurseNote AI            担当：山田 花子（3F東病棟）  [ログアウト] │
├──────────┬─────────────────────────────────────────────┤
│ 患者一覧   │ 田中 太郎（72歳／男性）　患者番号 P00123        │
│ [検索🔍]  │ 入院日 2026-07-26（16日目）                     │
│           │ 診断名：右大腿骨頸部骨折 人工骨頭置換術後         │
│ ●田中 太郎 │ ⚠ アレルギー：ペニシリン                        │
│  鈴木 花   ├─────────────────────────────────────────────┤
│  伊藤 健二 │ [入院時情報] [看護記録★] [退院サマリー]          │
│  渡辺 里美 ├─────────────────────────────────────────────┤
│           │ ① 過去 7 日間の看護記録（参照専用）              │
│           │ ② 本日の入力                                   │
│           │    バイタル ＋ チェック項目 ＋ 自由記述           │
│           │    [記録を生成 ▶]                              │
│           │ ③ 生成結果（編集可・黄色＝根拠なし）              │
│           │    [確定して保存]                               │
└──────────┴─────────────────────────────────────────────┘
```

### 3.2 入力設計：自由記述だけにしない

看護師にとって「文章を打つこと」自体が負担である。
自由記述のみの入力では、削減できるのは整形の手間だけで効果が限定的になる。

そこで本日の入力を 3 層に分ける。

| 層 | 入力方法 | 所要 |
|---|---|---|
| バイタル | 数値入力（体温・血圧・脈拍・SpO2・呼吸数） | 約 10 秒 |
| チェック項目 | チェックボックス（食事・排便・疼痛・移動・睡眠など） | 約 10 秒 |
| 自由記述 | **異常や変化だけ** を短く記入 | 約 20 秒 |

構造化された入力は LLM への指示としても明確であり、幻覚の発生率を大きく下げる。

### 3.3 記録様式の切り替え

日本の臨床現場では病棟・診療科により記録様式が異なるため、3 種類を選択可能とする。

| 様式 | 構成 |
|---|---|
| **SOAP** | S（主観的情報）/ O（客観的情報）/ A（アセスメント）/ P（計画） |
| **フォーカスチャーティング（DAR）** | Data / Action / Response |
| **経時記録** | 時刻順の叙述形式 |

## 4. バックエンド設計

### 4.1 技術選定

| 項目 | 採用 | 理由 |
|---|---|---|
| フレームワーク | FastAPI | 非同期対応、OpenAPI 自動生成、LLM ストリーミングとの相性 |
| ORM | SQLAlchemy 2.0（async）| 型注釈ベースのモデル定義、asyncpg 対応 |
| マイグレーション | Alembic | スキーマ変更の履歴管理 |
| 認証 | JWT（PyJWT）＋ bcrypt | ステートレス、シンプル |
| バリデーション | Pydantic v2 | LangChain の構造化出力と同じ仕組みを使える |

### 4.2 認証・認可

- ログインは **職員番号＋パスワード**。成功時に JWT を発行（有効期限 12 時間）
- トークンには `sub`（看護師 ID）、`ward`（所属病棟）、`role` を格納
- **病棟スコープ**：看護師は自分の所属病棟の患者のみ参照可能（`role = admin` は全病棟可）
  医療情報システムでは必須の要件であり、`app/api/deps.py:ensure_ward_access()` で実装

### 4.3 API 一覧

| メソッド | パス | 内容 | 実装 |
|---|---|---|---|
| GET | `/api/v1/health` | ヘルスチェック（DB 接続確認込み） | M1 ✅ |
| POST | `/api/v1/auth/login` | ログイン、JWT 発行 | M1 ✅ |
| GET | `/api/v1/auth/me` | ログイン中の看護師情報 | M1 ✅ |
| GET | `/api/v1/patients?q=&scope=admitted` | 担当患者検索（入院中のみ・既定） | M1 ✅ |
| GET | `/api/v1/patients?q=&scope=all` | 患者マスタ検索（入院登録用・検索語必須） | M1 ✅ |
| POST | `/api/v1/patients` | 患者マスタへの新規登録（患者番号は自動採番） | M1 ✅ |
| GET | `/api/v1/patients/{id}` | 患者詳細（入院情報・入院時基礎情報を含む） | M1 ✅ |
| GET | `/api/v1/patients/{id}/notes?days=7` | 直近 N 日分の看護記録 | M1 ✅ |
| POST | `/api/v1/admissions` | 新規入院登録 | M1 ✅ |
| POST | `/api/v1/admissions/{id}/discharge` | 退院処理 | M1 ✅ |
| GET | `/api/v1/notes/{id}` | 看護記録の単票取得 | M1 ✅ |
| POST | `/api/v1/notes/generate` | 看護記録の AI 生成（SSE ストリーミング） | M2 |
| POST | `/api/v1/notes` | 看護記録の保存・確定 | M2 |
| POST | `/api/v1/summaries/generate` | 退院サマリー生成 | M4 |

> 補足：`/patients/{id}/notes` は「今日から N 日前まで」ではなく
> **「記録が存在する最新日から N 日分」** を返す。
> 休日やデモデータで記録が飛んでいても直近の記録が確実に表示されるため。

### 4.4 データベース設計

```
nurses                    看護師（ログインユーザー）
patients                  患者マスタ（氏名・生年月日など。病棟は持たない）
  └ admissions            入院（病棟・病室・診断名・入院日・退院日）
      ├ admission_assessments   入院時基礎情報（1:1）
      ├ nursing_notes           日々の看護記録（1:N）
      └ discharge_summaries     退院サマリー（1:N）
audit_logs                監査ログ
```

主要テーブルの設計意図：

**病棟は患者ではなく入院に属する** — `ward` / `room` は `patients` ではなく
`admissions` に持たせている（マイグレーション `0002_ward_to_admission`）。

- 同じ患者でも入院ごとに病棟が変わりうる。入院中の転棟もある
- **入院していない患者は病棟を持たない。** `patients.ward` があると、
  未入院の患者にも架空の病棟が付いてしまい、担当患者一覧の判定が破綻する

この downgrade は非可逆である。`patients` は病棟を 1 つしか持てないため、
退院済みの入院や過去の入院分の病棟は復元できない。
これはスキーマとして `patients.ward` が誤りであったことの裏返しでもある。


**`nursing_notes`** — 1 レコードが 1 日 1 勤務帯の記録。
`(admission_id, record_date, shift)` に一意制約を設ける。

| カラム群 | カラム | 意図 |
|---|---|---|
| 看護師の入力 | `vitals` / `input_structured` / `input_free` | 生成の入力を JSONB でそのまま保存。再生成・検証・評価に使う |
| AI 生成結果 | `content_ai` | AI の生の出力。**上書きせず残す**（人がどこを直したかが分かる） |
| 確定版 | `content_final` / `status` / `confirmed_at` | 看護師が確認・修正した最終版。`confirmed` になって初めて正式記録 |
| 根拠 | `evidence_spans` | 生成文の各記述と、その由来（①直接事実 / ②歴史事実 / ③臨床的解釈）の対応表（M2） |
| 検証 | `verification` | 申告された根拠が実在するか、推論に飛躍がないかの裁定（M3） |
| トレーサビリティ | `model_name` / `prompt_version` / `token_usage` | どのモデル・どのプロンプト版で生成したか。医療システムでは後から追跡できることが必須 |

**`audit_logs`** — 「誰が・いつ・何をしたか」を記録。
ログイン、記録の生成、確定、修正がすべて対象。

**pgvector** — 拡張は M1 のマイグレーションで有効化済み。
埋め込み用テーブルは、使用する埋め込みモデルの次元数が確定する M3 で追加する。

## 5. LangChain 設計

### 5.1 検索方式の使い分け（重要）

「過去の記録をすべてベクトル化して検索する」という設計は、本ユースケースでは **誤り** である。
必要な情報の性質に応じて、SQL とベクトル検索を明確に使い分ける。

| 取得したい情報 | 方式 | 理由 |
|---|---|---|
| その患者の直近 7 日間の記録 | **SQL** | 範囲が明確で、**漏れが許されない**。ベクトル検索では重要な記録を取りこぼす |
| 患者の基本情報・アレルギー・禁忌 | **SQL** | 同上。安全性に直結する情報は確実に全件取得する |
| 類似症例の優秀な記録事例（Few-shot） | **ベクトル検索（pgvector）** | 意味的な類似性で選ぶため。動的 Few-shot として使う |
| 院内の用語集・略語表・記録規程 | **ベクトル検索（RAG）** | 典型的な知識ベース検索 |

> **他患者の記録がコンテキストに混入しないこと。**
> 記録取得のクエリは必ず `admission_id` で絞る。
> Few-shot 用のベクトル検索は他患者の記録を対象にするため、
> **必ず匿名化した「文体の見本」としてのみ渡し、事実の参照元にはしない。**
> この 2 つを混同すると、他患者の症状が生成文に混入するという最悪の事故が起きる。
> 検証層でも `patient_mismatch` として二重にチェックする（§5.3.3）。

### 5.2 Chain A：日次看護記録の生成（LCEL）

```python
chain = (
    RunnableParallel({
        "patient":      fetch_patient_profile,       # SQL
        "recent_notes": fetch_recent_notes(days=7),  # SQL
        "today":        RunnablePassthrough(),       # 本日の入力
        "examples":     example_retriever,           # pgvector（Few-shot）
        "glossary":     glossary_retriever,          # pgvector（用語集）
    })
    | build_prompt                       # 記録様式ごとのテンプレート
    | llm.with_structured_output(SOAPNote)
)
```

構造化出力のスキーマ（Pydantic）：

```python
SourceType = Literal[
    "today_input",         # ① 直接事実：本日の入力
    "historical_note",     # ② 歴史事実：過去の看護記録
    "patient_profile",     # ②' 患者背景：入院時基礎情報
    "clinical_inference",  # ③ 臨床的解釈：①②から導いた推論
]


class EvidenceItem(BaseModel):
    text: str                       # 生成文中の該当箇所
    source_type: SourceType
    source_ref: str | None          # "vitals.bt" / "note:123" / "profile.allergies"
    derived_from: list[str] = []    # ③ のとき、その推論が依拠した ①② の source_ref


class SOAPNote(BaseModel):
    subjective: str    # 本日の入力に無ければ空文字。推測での補完を禁止
    objective:  str    # 数値は入力値をそのまま使用
    assessment: str
    plan:       str
    evidence: list[EvidenceItem]
```

#### フィールド単位で許可する分類を変える

「臨床的解釈を一律に禁止する」という設計は採らない。
それをすると A（アセスメント）と P（計画）が生成できず、記録として成立しないためである。
代わりに **SOAP のどの欄に何を書いてよいか** を分類レベルで規定する。
これは臨床上の SOAP の定義とそのまま一致する。

| 欄 | 許可される `source_type` | 理由 |
|---|---|---|
| **S** | `today_input` のみ | 患者の発言そのもの。看護師が聞いていないことは書けない |
| **O** | `today_input` / `historical_note` / `patient_profile` | 観察された事実のみ |
| **A** | 上記すべて ＋ `clinical_inference` | アセスメントは本質的に解釈である |
| **P** | 上記すべて ＋ `clinical_inference` | 計画は解釈に基づいて立てられる |

この規則は **Pydantic の validator で機械的に強制できる**。
「S 欄に `clinical_inference` が混入した」は LLM の判断を待つまでもない構造的エラーであり、
その場で生成を却下して再試行させればよい。

#### `clinical_inference` には必ず `derived_from` を要求する

推論は、どの事実から導かれたのかを示せなければ検証できない。

```
「疼痛は前日と比較して軽減していると考えられる」
    derived_from = ["today.free_text#疼痛NRS3", "note:123#疼痛NRS5"]
```

これがあることで、画面上で「この推論の根拠」を展開表示でき、
看護師は推論そのものではなく **前提となった事実** を確認すれば済むようになる。

### 5.3 Chain B：根拠の検証（M3）

重要な区別として、`EvidenceItem.source_type` は **生成器が自己申告した由来** にすぎない。
その申告が正しいかを判定するのが Chain B である。

#### 5.3.1 「出典がある」ことは「内容が正しい」ことを意味しない

検証を `supported: bool`（＝出典の有無）だけで行うと、次のケースを取り逃がす。

```
本日の入力  : 体温 37.2℃
生成文      : 「体温 38.2℃ と発熱が持続している」
申告        : source_type = today_input, source_ref = "vitals.bt"
```

この記述は **出典の申告としては完全に正しい**。参照先も実在する。
それでも内容は誤っており、しかもバイタル値の誤りは臨床判断を直接誤らせる。
したがって検証は最低でも次の 5 点を見る必要がある。

1. 出典があるか
2. その出典が本当にその記述を支持しているか
3. **数値が一致しているか**
4. **時間の言及が整合しているか**
5. **患者が一致しているか**

#### 5.3.2 検証は 2 層に分ける（3〜5 は LLM に判定させない）

上記のうち **3・4・5 は決定的に判定できる**。
「38.2 と 37.2 は一致するか」を LLM に聞けばたいてい正答するが、
バイタル値の検証において「たいてい」は許容できる基準ではない。
機械的に比較できるものは、モデルを介さず Python で比較する。

| Layer | 手段 | 下す裁定 | 特性 |
|---|---|---|---|
| **Layer 1** | Python（LLM 呼び出しなし） | `value_mismatch` / `temporal_mismatch` / `patient_mismatch` | 決定的・100% 再現・追加コストゼロ |
| **Layer 2** | LLM（Chain B 本体） | `unsupported` / `contradicted` / `overreach` | 意味の判断が必要なもののみ |

Layer 1 で不合格になった記述は、Layer 2 に渡す前に確定する。
**安全上もっとも重大な誤りほど、モデルに依存しない経路で検出される**という構造にしておく。

```python
Verdict = Literal[
    # --- Layer 1（Python が決定的に判定）---
    "value_mismatch",     # 数値が入力と一致しない（37.2℃ → 38.2℃）
    "temporal_mismatch",  # 時間の言及が整合しない（3 日前の記録を「昨日」と書く）
    "patient_mismatch",   # 他患者の情報を参照している
    # --- Layer 2（LLM が意味を判断）---
    "unsupported",        # どの入力にも対応しない（＝捏造）
    "contradicted",       # 出典はあるが、内容が出典と矛盾する
    "overreach",          # 根拠は実在するが、そこから導けない飛躍がある
    # --- 合格 ---
    "verified",
]


class SpanVerdict(BaseModel):
    text: str
    claimed_type: SourceType    # 生成器の申告
    claimed_ref: str | None     # 生成器が指した出典
    verdict: Verdict            # 検証器の裁定
    layer: Literal["deterministic", "llm"]
    expected: str | None        # value_mismatch のとき、入力側の正しい値
    actual: str | None          # value_mismatch のとき、生成文にあった値
    reason: str


class VerifyResult(BaseModel):
    items: list[SpanVerdict]
```

```python
full_chain = (
    chain                                              # Chain A：生成
    | RunnablePassthrough.assign(det=run_deterministic_checks)   # Layer 1
    | RunnablePassthrough.assign(verification=verify_chain)      # Layer 2
)
```

#### 5.3.3 Layer 1 の各チェック

**`value_mismatch`** — 生成文から数値表現を抽出し、入力値と突き合わせる。

バイタル値そのものはテンプレートで埋め込むため改変されないが、
LLM は O / A / P の文章中でも数値に言及する（「発熱が持続しており 38.2℃」など）。
そこが検証対象になる。

正規化が必要な点：

| 論点 | 扱い |
|---|---|
| 単位 | `37.2℃` と `37.2` は同一とみなす |
| 複合値 | 血圧 `128/76` は収縮期・拡張期に分解して比較する |
| 表記ゆれ | `8割` と `80%` は同一とみなす |
| 丸め | `36.75` → `36.8` のような丸めは許容範囲を定義する |
| 判定不能 | 正規化しきれない表現は握りつぶさず **Layer 2 へ送る** |

**`temporal_mismatch`** — 日付演算で判定する。

- 「昨日」と書かれた記述の `source_ref` が 3 日前の記録を指している
- 「術後 2 日目」と書かれているが、`admitted_at` からの計算では 5 日目
- 「前日と比較して」と書かれているが、前日の記録が存在しない

**`patient_mismatch`** — SQL で判定する。

このエラーの主因は「LLM が患者を取り違える」ことではなく、
**検索層が別患者の記録を拾ってくる**ことである。したがって検証の実体は次の 1 行に尽きる。

```sql
-- 参照されたすべての note:N が、現在の入院に属していること
SELECT id FROM nursing_notes WHERE id = ANY(:refs) AND admission_id <> :current
```

ここに 1 件でも該当すれば `patient_mismatch`。判定に曖昧さは存在しない。

なお、これは **検索の時点でも防ぐ**（`admission_id` で必ず絞る）。
検証層の同チェックは二重の防御であり、
検索側の実装ミスを検知するための最後の砦として機能させる。

#### 5.3.4 裁定の重大度と確定操作

裁定はすべて同列ではない。**保存できるかどうか**まで規定する。

| 重大度 | 裁定 | 確定（`confirmed`）の扱い |
|---|---|---|
| **blocking** | `value_mismatch` / `patient_mismatch` / `contradicted` / `unsupported` | 該当箇所を修正するか、看護師が明示的に「確認済み」をチェックしない限り確定できない |
| **warning** | `temporal_mismatch` / `overreach` | 注意を促すが、確定は可能 |

確定を完全に禁止しないのは、記録を今すぐ残さなければならない臨床状況があるためである。
**「黙って保存させない」ことが目的であり、「保存させない」ことが目的ではない。**
確認済みチェックを付けて確定した場合は、その事実を監査ログに残す。

#### 5.3.5 画面表示

| 分類 / 裁定 | 表示 |
|---|---|
| ① `today_input` | 🟢 装飾なし（通常表示） |
| ② `historical_note` / `patient_profile` | 🔵 薄い下線。ホバーで参照元の記録日を表示 |
| ③ `clinical_inference` | 🟡 黄色背景。クリックで `derived_from` の根拠を展開 |
| warning（`temporal_mismatch` / `overreach`） | 🟡 黄色背景 ＋「要確認」バッジ |
| blocking（`value_mismatch` ほか） | 🔴 赤背景 ＋ 正しい値を併記（`38.2℃ → 入力は 37.2℃`） |

`value_mismatch` は「どこが違うか」ではなく **「入力では何だったか」** まで出す。
看護師が入力欄まで戻って確認する手間をなくすためで、
`expected` / `actual` を持たせているのはこのためである。

**すべてを強調しないことが重要である。**
①② は記録の大部分を占める通常のケースであり、これを派手に着色すると
画面が色だらけになって看護師は色を見なくなる。
目を引かせるのは 🟡 と 🔴 だけに絞る。

#### 5.3.6 保存

| カラム | 内容 |
|---|---|
| `nursing_notes.evidence_spans` | 生成器の申告（`EvidenceItem` の配列、M2） |
| `nursing_notes.verification` | 検証器の裁定（`SpanVerdict` の配列、M3） |

申告と裁定を別カラムに分けておくことで、
「生成器がどれくらい正直に申告したか」を後から評価できる。
これは M3 の評価セットで直接使える指標になる。

さらに Layer 1 の裁定は決定的なので、**評価セットの正解ラベルを人手で作らなくてよい**。
入力を意図的に改変した記録を投入すれば、期待される裁定は自動的に決まる。
これは LLM-as-judge に頼る Layer 2 の評価と比べて、はるかに信頼できる指標になる。

### 5.4 Chain C：退院サマリー（Map-Reduce）

入院期間が 30 日なら記録は 30 件以上になり、単一のコンテキストには収まらない。

```
Map    ： 入院期間を段階（急性期／回復期／退院前）に分割し、各段階を個別に要約
Reduce ： 要約を統合し、以下の構成で構造化出力
          入院時の状態 / 経過 / 実施したケア / 退院時の状態 /
          継続が必要なケア / 患者・家族への指導内容
```

### 5.5 運用上の工夫

| 項目 | 内容 |
|---|---|
| **プロンプトのバージョン管理** | `app/ai/prompts/v1/*.yaml` に外出しし、生成時に `prompt_version` を DB へ記録。A/B 比較と原因追跡が可能になる |
| **LangSmith によるトレース** | 実行トレースを収集。20 件程度の評価セットを用意し、LLM-as-judge で採点する。**ただし §5.6.5 の制約を必ず守る** |
| **送信データの最小化** | 外部 LLM へ送るのは、生成に必要な最小限のフィールドのみ（§5.6） |
| **ローカル LLM** | 院内運用では Ollama による完全オフライン動作を前提とする。これは選択肢ではなく既定である（§5.6.6） |
| **用語集の遵守** | `Vp`・`ADL`・`清拭`・`褥瘡` などの院内略語を用語集として RAG に載せ、プロンプトで遵守を指示する |

### 5.6 外部 LLM へ送るデータの最小化

#### 5.6.1 「氏名を伏せれば匿名」は成り立たない

当初この項目は「患者氏名を `【患者A】` に置換する」という設計にしていたが、
**これは対策として不十分であり、安全だという誤った印象を与えるため採用しない。**

医療情報における識別子は氏名だけではない。

| 種別 | 例 |
|---|---|
| **直接識別子** | 氏名、患者番号、電話番号、住所 |
| **準識別子（quasi-identifier）** | 年齢、性別、生年月日、入院日、退院日、病棟、診断名、家族構成 |

氏名を伏せても、次の 3 つが揃えば個人はほぼ特定できる。

```
72歳・男性
右大腿骨頸部骨折　人工骨頭置換術後
2026-07-26 入院　3F東病棟
```

病棟の規模は数十床であり、この母集団では **k-匿名性は実質 1 になる。**
氏名置換は直接識別子しか消していないため、再識別に対してほとんど効果がない。

さらに、看護記録は個人情報保護法上の **要配慮個人情報** にあたる。
第三者提供や国外事業者への越境移転には追加の要件がかかるため、
「氏名さえ伏せれば外部 API に送ってよい」という整理は成立しない。

#### 5.6.2 方針：マスキングではなく最小化

> ### 送るデータを加工するのではなく、そもそも送らない。

生成に不要なフィールドは、マスクするのではなく **AI 層へ渡さない**。

| フィールド | 送信 | 理由 |
|---|---|---|
| 氏名・カナ | ❌ | 生成文に氏名は登場しない（「患者は」と書く）。そもそも不要 |
| 患者番号 | ❌ | 生成に一切寄与しない |
| 生年月日 | ❌ | 年齢帯があれば足りる |
| 住所・電話・家族連絡先 | ❌ | AI 層のデータ構造に存在させない |
| 入院日・記録日（絶対日付） | ❌ | 後述のとおり相対日数に変換する |
| 年齢帯 | ⭕ | 「70代」。高齢者特有の表現選択に必要 |
| 性別 | ⭕ | 表現に影響する |
| 診断名 | ⭕ | 記録の中核。これが無いと生成できない |
| 病日（入院◯日目・術後◯日目） | ⭕ | 臨床的な意味を持つのはこちら |
| アレルギー・禁忌 | ⭕ | 安全に直結。必須 |
| バイタル・観察項目 | ⭕ | 記録の本体 |
| 過去記録の本文 | ⭕ | 直近 N 日分のみ。記載者名は除去する |

#### 5.6.3 実装は「許可リスト」で行う（除外リストではない）

ORM オブジェクトから不要な項目を削る実装にしてはならない。
カラムを 1 つ追加した瞬間、それが黙って外部へ送られるようになるためである。

**AI 層へ渡す専用の DTO を定義し、明示的に列挙した項目だけを詰める。**

```python
class LLMPatientContext(BaseModel):
    """外部 LLM へ渡してよい情報のみを保持する。
    ここに無いものは送られない。フィールド追加は必ずレビュー対象とする。"""
    age_band: str            # "70代"
    sex: str | None
    diagnosis: str | None
    hospital_day: int        # 入院◯日目
    post_op_day: int | None  # 術後◯日目
    allergies: list[str]
    chronic_diseases: list[str]
    diet_restrictions: str | None
    # 氏名・患者番号・生年月日・入院日は「意図的に存在しない」
```

除外リストは追加時に黙って壊れる（fail-open）。
許可リストは追加時に何も起きない（fail-safe）。
医療データを扱う以上、失敗の方向は必ず後者でなければならない。

#### 5.6.4 絶対日付を相対日数に変換する

これは **プライバシー対策であると同時に、生成品質の改善でもある。**

| 送らない | 送る |
|---|---|
| `2026-07-26 入院` | `入院16日目` |
| `2026-08-10 の記録` | `1日前の記録` |
| `2026-07-27 手術` | `術後15日目` |

臨床的に意味を持つのは「術後何日目か」であって暦上の日付ではない。
モデルにとっても相対日数のほうが解釈しやすく、
同時に最も強い準識別子のひとつである入院日が消える。**双方に利がある。**

#### 5.6.5 自由記述だけは検出が必要（fail-closed）

許可リストで守れるのは構造化データだけである。
**自由記述欄は看護師が何でも書けるため、ここだけは検出が要る。**

```
「息子の田中さんが面会。〇〇クリニックの△△医師へ連絡済み」
```

自由記述に対しては固有表現の検出を行い、
**判定できない場合は握りつぶさず、クラウド送信を中止する。**

| 検出結果 | 動作 |
|---|---|
| 個人名・施設名などを検出 | 該当箇所を提示し、看護師に修正を促す |
| 判定に自信が持てない | **クラウドへ送らず、ローカル LLM へフォールバックする** |

つまり PII 検出はシステムの中心的な防御ではなく、
**許可リストで守れない一点に限定して配置する最後の砦** である。

**トレース基盤にも同じ規約を適用する**

LangSmith にはプロンプト全文が送信される。
LLM への送信を慎重に設計しても、同じ内容をトレース基盤へ送っていれば意味がない。

> **LLM への送信に課す規約は、LangSmith・アプリケーションログ・エラー通知にも
> そのまま適用する。** 例外を作らない。

院内運用では LangSmith を無効化するか、セルフホストする。

#### 5.6.6 デプロイ形態ごとの整理

**データ最小化はクラウド利用を適法にする手段ではない。**
送信すべき臨床内容そのものが識別性を持つため、最小化には下限がある。

| 形態 | LLM | データ | 位置づけ |
|---|---|---|---|
| **開発・面接デモ** | クラウド（DeepSeek / Qwen） | **架空のシードデータのみ** | 実患者データを一切使わないため成立する |
| **院内運用** | **Ollama（院内・外部送信なし）** | 実データ | これが既定。クラウドは選択肢に入らない |

`LLM_PROVIDER` 環境変数で切り替えるが、**既定値は `ollama` とする。**
クラウドを使う場合は `ALLOW_CLOUD_LLM=true` を明示的に指定させ、
起動時に警告ログを出す。事故の方向を「うっかりクラウドへ送る」ではなく
「うっかりローカルで動く」側に倒すための設計である。

## 6. フロントエンド設計

### 6.1 方針

**ビルドツールを使わない。外部ライブラリは Vue 3 のみ。**
CDN から Vue を読み込むだけの、素の HTML/CSS/JS で構成する。

| 役割 | 採用 |
|---|---|
| 画面状態の管理と描画 | Vue 3（Options API、グローバルビルド） |
| API 通信 | ブラウザ標準の **fetch API**（追加ライブラリなし） |
| スタイル | 素の CSS（フレームワークなし） |

理由：本プロジェクトの主眼は LangChain によるバックエンド設計にあり、
フロントエンドはビルド工程を持たないほうが保守しやすく、動作確認も容易なため。

通信ライブラリを別途入れないのは、**Vue が担うのは描画であって通信ではない** ため。
HTTP 通信はブラウザ自身が `fetch` として持っており、jQuery や axios のような
ライブラリを重ねると、依存が増えるだけで役割が重複する。

fetch には注意点が 2 つあるため、`app.js` の `api()` 関数に閉じ込めている。

1. **404 や 500 でも例外にならない** — 「通信自体は成功した」と見なされるので、
   `res.ok` を自分で確認して `ApiError` を投げ直す
2. **戻り値は生のレスポンス** — `res.json()` で中身を取り出す必要がある

呼び出し側は `await api('GET', '/patients')` と書くだけでよく、
エラーは `try / catch` で日本語メッセージ（`e.detail`）として受け取れる。

### 6.2 ファイル構成

```
frontend/
├─ nginx.conf          静的配信 + /api リバースプロキシ
└─ html/
   ├─ index.html       画面のマークアップ（Vue テンプレート）
   ├─ app.js           api() ラッパー ＋ Vue アプリ（状態管理）
   └─ style.css        スタイル
```

### 6.3 認証の扱い

JWT を `localStorage` に保存し、`api()` が毎回のリクエストに
`Authorization: Bearer` ヘッダーとして自動で付与する。
リロード時は `/auth/me` でトークンの有効性を確認してから画面を復元し、
401 が返った場合はトークンを破棄してログイン画面に戻す。

### 7.2 環境変数

M1 では LLM を使用しないため、`docker-compose.yml` 内の環境変数のみで動作する。
M2 で LLM を接続する際は `.env.docker` を作成し、compose の `env_file` を有効化する。

```
# 既定はローカル。外部送信は明示的に許可しない限り行わない（§5.6.6）
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://ollama:11434
OLLAMA_MODEL=qwen3:8b

# --- クラウド LLM を使う場合のみ ---
# ALLOW_CLOUD_LLM=true       # 未設定ならクラウドへは一切送信しない
# LLM_PROVIDER=deepseek
# DEEPSEEK_API_KEY=...
# DEEPSEEK_BASE_URL=https://api.deepseek.com

# --- トレース ---
# プロンプト全文が LangSmith へ送られる。LLM と同じ規約を適用すること（§5.6.5）
LANGSMITH_TRACING=false
# LANGSMITH_API_KEY=...
```

> `LLM_PROVIDER` の既定値は `ollama`、`ALLOW_CLOUD_LLM` の既定値は `false`。
> 設定を忘れた場合に起きるのは「ローカルで動く」であって
> 「気づかずクラウドへ送信する」ではない。

#### 臨床的解釈（③）の段階的な扱い

| フェーズ | `clinical_inference` の扱い |
|---|---|
| **M2** | **S / O 欄では禁止**（validator が構造的に拒否）。A / P 欄では許可するが、`derived_from` を必須とする。画面では 🟡 で色分けするのみで、内容の検証はまだ行わない |

M2 の時点で「解釈は A / P にしか置けない」という構造だけは強制しておく。
この制約は LLM の判断に依存せず Pydantic で機械的に効くため、
検証チェーンが無い M2 の段階でも安全性の下限を確保できる。

### V2（LangGraph 版）で扱う内容

V1 は LCEL による線形のチェーンで構成する。V2 では LangGraph に置き換え、
LCEL では表現しにくい **ループと分岐** を導入する。

- 生成 → 検証 → 不合格の裁定があれば **自動で再生成**（最大 2 回）
  → 解消しなければ `interrupt()` で人間に委ねる。**裁定の種類ごとに再生成の指示を変える**

  | 裁定 | 再生成時の指示 |
  |---|---|
  | `value_mismatch` | 入力値（`expected`）で置き換えさせる。ここは決定的なので修正も決定的にできる |
  | `unsupported` | 該当箇所を削除させる |
  | `overreach` | 断定を弱めさせる（「〜と考えられる」「〜の可能性がある」） |
  | `temporal_mismatch` | 時間表現を `source_ref` の実日付に合わせさせる |
  | `patient_mismatch` | **再生成しない。** 検索層のバグなので即座に停止して報告する |

- checkpointer による対話的な修正（「もっと簡潔に」「疼痛の記述を詳しく」）
- Human-in-the-loop を明示的なノードとして組み込む

なお `value_mismatch` は、そもそも LangGraph を待たずに **決定的な後処理で直せる**
（正しい値が分かっているため）。V2 で LLM に再生成させるのは、
文全体の自然さを保ちたい場合に限る。

V1 と V2 を比較できることで、「なぜ LangGraph が必要になるのか」を具体的に説明できる。

## 9. 制約事項・注意点

1. **実在の患者データは一切使用しない。** 本リポジトリのシードデータはすべて架空の人物・架空の経過である
2. **数値は LLM に生成させない。** バイタル値はテンプレートで直接埋め込む
3. **事実と解釈を混ぜない。** 生成文のすべての記述に `source_type` を持たせ、
   臨床的解釈は A / P 欄に限定し、必ず `derived_from` で根拠を示させる
4. **出典があることを、内容が正しいことの証明として扱わない。**
   数値・日付・患者の一致は LLM に判定させず、Python / SQL で決定的に検証する
5. **他患者の記録を事実の参照元にしない。** Few-shot 用の類似事例は
   匿名化した文体の見本としてのみ使う
6. **外部 LLM へは必要最小限のフィールドしか送らない。** 氏名の置換ではなく、
   許可リスト DTO による最小化で担保する。**氏名を伏せても準識別子で再識別されうる**
7. **外部送信の規約はトレース基盤・ログにも同じく適用する。** 例外を作らない
8. **院内運用ではローカル LLM を既定とする。** クラウド利用は明示的な許可を要する
9. **生成物は下書きである。** 看護師が確認・確定するまで正式な記録として扱わない
10. **記録の最終責任は看護師にある。** この旨を画面上にも常時表示する
